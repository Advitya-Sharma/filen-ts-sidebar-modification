# Assistant

An AI assistant that runs entirely on the user's device. A small open-weights model (GGUF, run by [wllama](https://github.com/ngxson/wllama), llama.cpp compiled to wasm) answers questions about the user's drive, notes, chats, photos and music, navigates the app, and drafts chat messages. Nothing the user asks or the assistant reads leaves the device.

Paths starting with `packages/` are from the repo root, `src/`, `vite/` and `scripts/` from `packages/filen-web`, the rest from this directory.

## Hard rules

- **On-device only.** No inference service, no telemetry. The only new network traffic is the model download from the Filen CDN; tools read data through the app's usual end-to-end encrypted requests and caches.
- **Opt-in.** Nothing is downloaded until the user clicks Download in the panel. The model loads into memory only on an explicit request (a sent message or the Load action), never because the panel opened.
- **Nothing is ever permanently deleted.** No tool can delete permanently, empty the trash, unshare, leave, change links or touch the account. Removal can only mean the restorable trash, and only after a confirmation.
- **Read and navigate, plus confirmed drafts.** The web app runs read, navigation and `draft_chat_message` tools (`ASSISTANT_WEB_TOOLS`). A draft only fills the chat composer; the user still presses Send. The shared registry already defines writes (move, rename, trash, ...); the web app does not offer them yet.
- **Safety is enforced in code, never by the model.** Text other people write (shared item names, note and file contents, chat messages) can steer the model, so:
    - _scope_: the router reads only the user's own words and picks one tool group plus read/change; a turn can call only that group's tools (the model is shown those of the group's whole prompt family, the loop refuses the rest) and a read turn never gets consequential tools;
    - _grounding_: a consequential call's handles must trace back to the user (the screen context, a lookup the user asked for, a name the user typed); new names, recipients and destinations must appear in the user's own message;
    - _taint_: once a turn has read other people's content, consequential tools and `open_route` are withdrawn for that turn;
    - _sanitize / quarantine_: untrusted strings lose chat-template control tokens (including the loaded model's own special tokens, read from the GGUF header) and invisible/bidi characters; note bodies, file text and chat messages are summarized by a tool-less extraction call before the main loop sees them;
    - _reply screen_: links and addresses the user did not type are defanged, a reply that echoes the system prompt (its per-conversation canary or an instruction line) is withheld, and replies render as markdown with no live links or images;
    - _confirmation_: a consequential call runs only from a confirmation card clicked by a trusted, browser-dispatched event (`components/userActivation.ts`), never from script or the model;
    - _import ban_: [`eslint.config.js`](../../../eslint.config.js) forbids `src/features/assistant/**` and the worker from importing irreversible or security-critical operations, the raw SDK, settings/auth modules, and any dynamic `import()`. [`src/tests/assistantImportRestrictions.test.ts`](../../tests/assistantImportRestrictions.test.ts) pins the rule.

## Model lifecycle

- **Device check** (`deviceCheck.ts`): desktop browsers with wasm SIMD, exceptions, Memory64 and OPFS, and at least `MIN_DEVICE_MEMORY_GIB` where the browser reports memory. WebGPU when JSPI is present, the adapter can bind 1 GiB buffers and the browser is not Firefox; otherwise the CPU path, which needs cross-origin isolation and at least 2 threads (half the cores, at most 8). Mobile browsers are refused. A failed WebGPU load falls back to the CPU path in a fresh worker.
- **Download**: shards are fetched 3 at a time, largest first, hashed as they arrive (a hasher checkpoint beside each partial shard), resumed with `Range` after stalls, errors, reloads or crashes, and recorded in `verified.json` only once their sha256 matches the pinned manifest. A download without room for the rest of the model is refused (`navigator.storage.estimate()`), and persistent storage is requested from the click.
- **Explicit load, idle unload**: the worker exists only while downloading or running; terminating it frees the engine's memory and GPU device. The model unloads after `IDLE_UNLOAD_MS` without activity (wall clock, also re-checked on visibility change), panel open or not. An unanswered card expires after `CARD_EXPIRY_MS` so it cannot pin the model.
- **One tab**: the Web Lock `filen-assistant-model` is held while a tab downloads or runs the model. Other tabs show it as in use elsewhere and re-check when the lock is released, so OPFS is never written by two contexts.
- **Router prompt priming**: the router's system prompt is fixed. At load the worker reads it once in the model's ChatML layout, so every router request reads only the user's message; after a turn it is read again if a request found it evicted (`reprime`). Priming applies only to ChatML templates.
- **Cache sizing**: one unified KV cache of `ASSISTANT_CONTEXT_TOKENS + ROUTER_CONTEXT_TOKENS + QUARANTINE_CONTEXT_TOKENS` with 3 slots (router, main loop, extraction), idle-slot caching off, and `MAX_STEPS + 2` context checkpoints. Qwen3.5 is a hybrid model that resumes a cached prompt only from a stored state checkpoint; [`patches/@wllama__wllama@3.8.1.patch`](../../../../../patches/@wllama__wllama@3.8.1.patch) passes `n_ctx_checkpoints` through to the engine. Keep prompts prefix-stable: every main request renders the tools of its group's prompt family (`ASSISTANT_PROMPT_FAMILIES`: drive/trash/sharing, organize, insights, notes/chats, music/navigation) in one fixed order, so a route change within a family reuses the prompt (the chat template puts the tools first; a per-group list made every route change read the whole conversation again), and a return to an earlier family resumes the copy the engine moved to its host-memory prompt cache when another family took the slot. The answer route renders no tools (shown tools it may not call, the model tries them and answers worse). The system prompt changes only with the family (its unavailable-tools line), per-turn data (date, screen context, and the names of the tools this request may call when the family shows more) goes in the user turn, and conversation history only grows within its budget before it is cut back to half. What a request may call is enforced by the loop and the guard, never by what the model is shown.

## Adding or changing a tool

1. **Define it** in `packages/filen-shared/src/assistant/tools.ts` with `defineTool`: a snake_case name, a `title` (named in the prompt while the app cannot run the tool), a description the model reads, its home `group`, a flat `z.strictObject` input inside the portable subset (string, integer, boolean, enum, scalar arrays; every property described; no nesting, unions, floats, bounds, formats, patterns or defaults), and the guard metadata: `effect` (`read`/`navigate`/`additive`/`modifying`), `untrustedOutput` (`none`/`names`/`content`), `exfiltrates`, and `grounded` (which arguments are handles, free text or link-bearing text). `additive`, `modifying` and `exfiltrates` make it consequential. Take items by handle, never by UUID; take dates as `period`/`from`/`to` and resolve them with `dates.ts`.
2. **Route it**: add it to `ASSISTANT_TOOLS` and to one or more groups in `ASSISTANT_TOOL_GROUPS` (at most 6 tools per group, the home group included; update the group description if the router must learn new phrasing). Add it to `ASSISTANT_WEB_TOOLS` once the web app runs it.
3. **Shared tests** (`packages/filen-shared/src/tests/assistantTools.test.ts`) lint every schema, enforce the group size, and pin the lists of modifying, consequential, exfiltrating and content-returning tools; change those pins deliberately.
4. **Web adapter**: write it in `tools/<area>.ts` and register it in `ADAPTERS` (`tools/executor.ts`, typed so a missing web tool fails typecheck). Every list of items (records with a `handle`; not `transfers`, whose rows gain one only once their item exists) reaches the model as one line per item (`f3 ⟦CV.pdf⟧ in=⟦/Documents⟧ size=1.2 MB`, `serializeToolResult`), and prompt tokens are most of a step's wait in the browser, so a row carries only what the model needs: `handle`, `name` or `title`, then few fields. A long listing pages with `listingPage`: `offset` in, `more` and `next` (the following page's offset) out. Register every item the result names through the scope (`show`) so the guard and handles know it, report long work through `progress`, honour the signal, and go through the feature modules the user's own actions use (the ESLint ban keeps the raw SDK out). Add the step label to `TOOL_ACTIVITY_KEYS` (`components/assistant.logic.ts`) and `src/locales/en/assistant.ts`. A consequential tool also needs a card in `loop/executorAdapter.ts`; without one it cannot run.
5. **Eval**: implement it in `packages/filen-assistant-eval/src/fakeApp.ts` (data in `fixture.ts`), add cases under `src/cases/` in several languages, injection cases if it returns other people's text, and run the gate below.

## Development

- `pnpm run dev` serves the assistant against the production model from the CDN unless configured otherwise.
- `VITE_ASSISTANT_MODEL_BASE_URL` points a build at another directory of model files (https, or http on localhost). `vite.config.ts` adds its origin to `connect-src`. The pinned manifest still applies, so the host must serve exactly the pinned files.
- `FILEN_ASSISTANT_DEV_GGUF=/abs/path/model.gguf pnpm run dev` (or the first piece of a split model) serves a local model through the dev-only plugin in [`vite/assistant-model.ts`](../../../vite/assistant-model.ts) under `/__assistant-model/`, with a manifest hashed on first request. It applies only in dev builds without `VITE_ASSISTANT_MODEL_BASE_URL`. A completed download removes other models from OPFS, so switching between dev and shipped models downloads again.

## Hosting and updating the model

- **Host constraints** (`cdn.filen.io/gguf/`): only CORS-simple requests work (the host answers `OPTIONS` with 405), so the download sends no header except a single `Range: bytes=N-`, with `credentials: "omit"` and `cache: "no-store"`. `Content-Range` is not exposed; a resumed response is recognized by status 206 and `Content-Length`. The host must send `Access-Control-Allow-Origin` and honour `Range`.
- **Split** the upstream GGUF with llama.cpp's `llama-gguf-split --split-max-size 512M <model>.gguf <prefix>`, which writes `<prefix>-0000N-of-0000M.gguf`. wllama cannot load a file over 2 GB without JSPI, and smaller pieces resume and verify independently. Publish the pieces (and, for runtimes without that limit, the unsplit file) under new names; never overwrite a published file, since deployed builds pin its hash.
- **Pin** the files: `pnpm exec tsx scripts/assistant-model-manifest.ts /path/to/<prefix>-00001-of-0000M.gguf` prints the `shards` list (sizes and sha256) for a new manifest in `runtime/models.ts` with a new `id`; run it on the unsplit file for the optional `whole` entry. `parseManifest` rejects pieces out of llama-gguf-split order or over 2 GB.
- **CSP**: the default host is inside `connect-src`'s `https://*.filen.io`; any other host needs `VITE_ASSISTANT_MODEL_BASE_URL` at build time (see above).
- A different model family also needs its chat template, tool-call format, thinking mode and special tokens checked in the worker (priming assumes ChatML) and a full eval run.

## Eval gate

Every model-facing change (prompts, tool definitions or descriptions, groups, guard, sanitizing, context or history layout, the model or its settings) is measured with [`packages/filen-assistant-eval`](../../../../filen-assistant-eval/README.md), which runs this exact shared loop on a fake app. Run it before and after on the shipped model with the `shipped` preset: no regression in pass rate or routing, and 0 executed / 0 leaked on the injection suite. Add cases for the new behaviour.
